torch → vLLM → Inductor → Triton

A call-flow book — captured live from Qwen2.5-0.5B on an RTX 4090 (CUDA) and on CPU. Every kernel, graph, and log line below is real output from a run on this machine, not a sketch.

The whole book in one sentence: every operation in a vLLM forward pass ends up as compiled machine code — the only questions are who writes the kernel and when. torch.compile watches the model run once and writes down what it did (an FX graph); vLLM's backend cuts that graph at every attention and hands the pieces to Inductor; Inductor writes the actual kernel — Triton on GPU, C++/OpenMP on CPU. Same front-end, two terminals.

The stable color code — it means the same thing on every diagram, badge, and code highlight in this book:

PART I · THE COMPILE PIPELINE

STAGE 1  Where it starts: @support_torch_compile

Plain version: vLLM doesn't hand your model to the compiler and wait. It puts a sticky note on the model class that says "compile me the first time you run" — then goes on loading weights. The real compilation only fires later, during a warm-up dummy forward. So all the "compiling…" noise in the logs shows up at startup, not on your first request.

Every compilable model class (here Qwen2Model) is decorated. The decorator rewrites the class: it mixes in a wrapper base and installs a custom __call__ that decides, on every invocation, between running eager and running the compiled artifact.

# vllm/model_executor/models/qwen2.py
@support_torch_compile        # decorators.py:118 → rewrites the class
class Qwen2Model(nn.Module):
    def forward(self, input_ids, positions, ...): ...
Registered at construction wrapper.py:90 → 148

When the model is built, the wrapper calls init_backend() to get a VllmBackend instance, then torch.compile(self.forward, fullgraph=True, backend=VllmBackend). This only registers — no tracing yet.

Compiled at warm-up gpu_model_runner.py:6262 → 6322

profile_run → _dummy_run runs the model once with fake inputs. That first call triggers Dynamo tracing → split → Inductor → Triton, all up front.

Gotcha #1 — mode decides everything. Only VLLM_COMPILE (mode 3, the v1 default) produces the VllmBackend → split → piecewise path this book traces. STOCK_TORCH_COMPILE (mode 1) returns early after a plain nn.Module.compile() and never touches any of it compilation.py:1057–1071.

STAGE 2  The split: attention is the seam

Plain version: a compiler loves one big graph, but attention can't be baked into a static kernel — it reads and writes the paged KV cache and has its own hand-written kernel. So vLLM cuts the graph at every attention op, compiles the math between the cuts, and runs attention eagerly in the gaps. Click a node to see how the seam falls.

STAGE 3  Inductor: the torch → kernel boundary

Plain version: each compute-piece is now a small graph of plain math ops. Inductor is the part of PyTorch that turns such a graph into a real kernel — it fuses the ops, then writes source code and compiles it. This is the single door every piece walks through; the target platform decides what language comes out the other side.

vLLM calls Inductor through an adaptor. In this run the log shows Using InductorStandaloneAdaptor — the torch-2.8+ path that calls torch._inductor.standalone_compile compiler_interface.py:280 → 376. Just before that, vLLM's own post-grad passes rewrite the vllm_ir ops (like fused_add_rms_norm) into plain ATen ops that Inductor can fuse VllmIRLoweringPass.

Gotcha #2 — the vllm_ir lowering lives in the backend, not in stock Inductor. If you call torch.compile(backend="inductor") directly (no VllmBackend), the vllm_ir.fused_add_rms_norm node stays opaque and is not fused into the kernel — you'll see it survive as an extern call. The fusion you see below only happens on the full VLLM_COMPILE path. (Verified on CPU — see the colophon.)

// emitted via async_compile.cpp_pybinding — vectorized with at::vec
extern "C" void kernel(const at::BFloat16* in_ptr0, const at::BFloat16* in_ptr1,
                       float* out_ptr0, at::BFloat16* out_ptr1) {
  #pragma GCC ivdep
  for (int64_t x0 = 0; x0 < 8L; x0 += 1L) {            // one row per outer iter
    at::vec::VectorizedN<float,2> tmp_acc0_vec = ...;
    for (int64_t x1 = 0; x1 < 896L; x1 += 16L) {       // 16 bf16 lanes / step
      auto tmp0 = at::vec::Vectorized<at::BFloat16>::loadu(in_ptr0 + x1 + 896L*x0, 16);
      auto tmp1 = at::vec::convert<float,2,at::BFloat16,1>(tmp0);
      auto tmp2 = tmp1 * tmp1;                          // x^2
      tmp_acc0_vec = tmp_acc0_vec + tmp2;               // Σ x^2  (vector reduce)
    }
    // ... vec_reduce_all → / 896 → rsqrt(+eps) → * weight → store bf16
  }
}

Same three-phase shape as the Triton kernel: reduce Σx², then rsqrt(mean+eps), then scale by weight — but expressed as an at::vec::Vectorized loop the C++ compiler turns into SIMD.

STAGE 2 (runtime)  CUDA graphs — the orthogonal driver

Plain version: compiling the kernels is one thing; launching 49 of them per token, per request, has its own overhead. A CUDA graph records the whole launch sequence once and replays it as a single call. It's a separate mechanism layered on top of the compiled pieces — not part of the compile itself.

At warm-up vLLM captures graphs for a fixed set of batch sizes cuda_graph.py:283 · 313. Our run used mode FULL_AND_PIECEWISE:

# captured log
Capturing CUDA graphs (FULL):      100%|██████████| 4/4
Capturing CUDA graphs (PIECEWISE): 100%|██████████| 5/5   # sizes [1, 2, 4, 8, 16]
Gotcha #3 — two independent wrappers. PiecewiseBackend (dispatches the compiled piece for a shape) and CUDAGraphWrapper (capture/replay keyed by the runtime batch descriptor) are separate. A descriptor mismatch makes the graph wrapper silently fall back to eager cuda_graph.py:254 — "no cudagraph" is not an error, so it's easy to miss in a log.

PART II · REACHING THE HARDWARE & PORTING A DEVICE

Kernels only matter if they reach your hardware. The PyTorch dispatcher routes every op by device key — and exactly one thing, vLLM's Platform, must recognize your device. The compile knob and the custom kernels sit on top; both optional.

FOUNDATION  The layer cake — what's mandatory, what's optional

Plain version: three different things decide how your model runs, and they get mixed up constantly. Stack them right: Platform is the foundation that makes vLLM recognize your device — you cannot skip it. Above it sit two optional layers: vLLM's hand-written csrc kernels (per-op) and the compile knob. And one band stays load-bearing even after you drop the optional layers: attention + KV-cache are always compiled.

BEYOND TRITON  What Inductor actually emits — & porting it to a new device

Plain version: Inductor's output is not one big Triton kernel — it's a small Python wrapper that mixes three kinds of line, all running on the same device's tensors. When you port to a new device, those three kinds collapse into two completely separate registration jobs — and neither is vLLM's Platform; both live in PyTorch.

A  How the dispatcher routes — and why you never patch it

Plain version: the PyTorch dispatcher is a fixed routing table, not code you edit. You don't change it — you register kernels into it. Once your tensor carries the right device key and a kernel is registered under it, routing is fully automatic — no if device==... anywhere. So "automatic" is true of the routing; the registration is the work.

The table is keyed by DispatchKey — 147 of them, compiled into libtorch, so you can't add one at runtime. A brand-new device therefore claims the reserved PrivateUse1 slot. Three steps make aten::* auto-route to your hardware:

  1. Claim the key — rename PrivateUse1 to your device (all verified present in torch 2.11): 
    torch.utils.rename_privateuse1_backend("mydev")
torch._register_device_module("mydev", my_module)        # streams, device_count, …
torch.utils.generate_methods_for_privateuse1_backend()   # .to("mydev"), Tensor.is_mydev
  2. Make tensors carry the key so torch.empty(device="mydev") yields a PrivateUse1-keyed tensor: an allocator (REGISTER_ALLOCATOR), empty_strided/factory ops, and a DeviceGuard (C10_REGISTER_GUARD_IMPL(PrivateUse1, …)) for stream/device. No backend → no tensor → nothing to route.
  3. Register kernels under the key: 
    TORCH_LIBRARY_IMPL(aten, PrivateUse1, m) { m.impl("mm", &my_mm); … }
// or in Python:  torch.library.impl("aten::mm", "PrivateUse1", my_mm)

Then extern_kernels.mm → aten::mm(device="mydev") → the dispatcher looks up (mm, PrivateUse1) → your kernel, with zero Python branching. An op you didn't register hits your fallback (m.fallback(…) can forward to CPU) or raises "not implemented for PrivateUse1" — precisely the failure in the self-test counterfactual.

vLLM's only role in routing is a label. Platform.dispatch_key="PrivateUse1" just tells vLLM what your key is (to assemble custom-op registration sets); it never touches the dispatcher itself. torch-side = the 3 steps above; vLLM-side = set that string + ship the Platform/Worker/Attention classes.

B  Making Inductor emit code for your device

# (B) — verified present in the installed torch 2.11:
torch._inductor.codegen.common.register_backend_for_device(
    device, device_scheduling, device_wrapper_codegen, ...)   # TritonScheduling / CppScheduling
torch._dynamo.device_interface.register_interface_for_device(device, interface)
# already-registered interfaces: ['cpu', 'cuda', 'mps', 'mtia', 'xpu']
Escape hatch. compilation_config.backend="eager" (or enforce_eager=True) → no Inductor → the whole graph is dispatcher ATen. Now you need only (A), not (B). That's why eager-first bring-up is the pragmatic path: get the model running on your ATen backend, invest in Inductor codegen for speed later.
Orthogonal to vLLM. None of this is vLLM's Platform. vLLM's backend knob only chooses inductor / eager / a custom CompilerInterface; whether Inductor can actually target your device is decided entirely by the two PyTorch registrations above. Precedent: Intel's out-of-tree intel_extension_for_pytorch called both for "xpu" before it went in-tree.
