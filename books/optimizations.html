唯一的想法

GPU 服務一個大語言模型時,它的每一毫秒只花在三件事之一:算(做浮點運算)、 搬(把位元組搬進搬出顯示記憶體)、等(kernel 啟動、同步、CPU 簿記)。第四本帳裝 (記憶體容量)不直接花時間,但它決定你能疊多大的批次——而批次大小決定你是在「算」還是在「搬」。 vLLM 裡的每一個優化,都是在還這四本帳的其中一筆債;它值不值得,取決於你當下的 regime (prefill 還是 decode)哪個債主上門。這本書的其餘部分全是這句話的細節。

四本帳,顏色全書固定——每張圖、每個徽章、每個目錄項都用同一套:

它是什麼病徵主要藥方(章)
搬 move位元組進出 HBM:權重、KV cache、中間物字與字之間慢(ITL 高);batch 加大吞吐才上升FlashAttention(3)、投機解碼(4)、KV/權重量化
算 compFLOPs:GEMM、attention 分數首字慢(TTFT 高);GPU 利用率吃滿仍慢更強的 kernel、量化、形狀特化 kernel(6)
等 waitkernel launch、同步、CPU 排程、通訊延遲batch 小、模型小,延遲卻下不去;GPU 有空隙融合、CUDA Graphs(5)、高效排程
裝 fitHBM 容量:權重 + KV + 激活OOM;batch 上不去 → 吞吐被鎖死PagedAttention / 前綴快取(2)、LoRA(6)、量化
這本書怎麼讀
第 1 章用本機實測建立全書的座標系:同一顆 RTX 4090 上,prefill 每 token 14.6 µs、 decode 每 token 5.25 ms——359 倍。第 2–6 章每章還一本帳,能實測的都附本機 capture (青色框,重現指令見 Colophon)。第 7 章是互動決策樹: 挑一個病徵,看它被路由到哪個處方。第 8 章是本書的核心:一步 decode 的活地圖—— 點左邊的每一行,右邊亮起它欠的帳與攻擊它的優化。▶ 後面是選讀深度。 每個宣稱都掛著一顆像 scheduler.py:396 的藥丸,連到釘選 commit 的那一行原始碼。深挖系統機制時,姊妹書 《vLLM 之書》有整章展開;本書專注「為什麼快」。
第 1 章

兩個 regime:時間都花在哪

一個 request 的一生分兩段:prefill(一次吃完整個 prompt)與 decode(每步吐一個字)。兩段做的數學一樣,經濟學卻完全相反——prefill 把一次權重讀取 攤給幾千個位置,decode 每個字都把幾 GB 權重從頭讀一遍。先看錢花在哪,才知道哪個優化值得買。點下面每一站:

座標系:本機實測 359×

實測 capture R — RTX 4090 · Qwen2.5-0.5B · batch=1 · eager · 前綴快取關閉
[R0] prompt_a=961 tok, prompt_b=897 tok, decode_steps=128
[R1] prefill: 14.1 ms total -> 14.6 us/token
[R2] decode : 672.1 ms for 128 steps -> 5.25 ms/token
[R3] per-token cost ratio decode/prefill = 359x

同一個模型、同一顆卡、同樣的每 token 數學,成本差 359 倍。原因不是計算,是搬運的攤提:

一次 forward 讀權重產出 logits每 token 的權重讀取bound
prefill(961 tok)1 次961 份1/961 次算算術強度高,吃滿 Tensor Core
decode(每步)1 次1 份1 次搬讀 1GB 權重算幾百萬 FLOP

這給出全書反覆使用的三條推論:

  • prefill 的優化要省「算」與 N² 的中間物 —— 第 3 章 FlashAttention 的地盤。
  • decode 的優化要省「搬」:要嘛讓一次權重讀取產出更多 token(第 4 章投機解碼、continuous batching), 要嘛把要搬的位元組變少(KV/權重量化)。
  • decode 的單步工作太小,「等」也開始顯形 —— 幾百個微小 kernel 的啟動費(第 5 章融合)。
裝(fit)是槓桿,不是時間
continuous batching 把 256 個 decode 疊進同一步:權重仍然只讀一次,卻產出 256 個 token—— 「搬」被攤成「算」。而你能疊多大的 batch,取決於 KV cache 裝得下多少 request。 這就是為什麼第 2 章(容量)排在所有時間帳之前:容量是把搬轉成算的籌碼。 排程端的機制(token 預算、兩階段)在《vLLM 之書》第 2 章;本書只取它的經濟意義。
選讀:為什麼「讀權重」主宰 decode——一筆信封背面的帳

0.5B 模型 bf16 權重 ≈ 1 GB。4090 的 HBM 頻寬 ≈ 1 TB/s,光讀權重的下限就是 ~1 ms/步; 實測 5.25 ms 還包含 KV 讀取、啟動費與未飽和的頻寬。而這一步的計算量(batch=1)約 2×0.5G = 1 GFLOP, 對 4090 的 ~80 TFLOPS(bf16)只是 ~0.01 ms 的活——算力閒著,頻寬滿載。 把 batch 疊到 256,計算變 256 GFLOP(~3 ms)而權重讀取不變:兩者打平,regime 從搬轉算。 這條「多大 batch 才轉 regime」的分界線,就是 roofline 模型的脊點。

第 2 章 · 裝 fit

PagedAttention 與前綴快取:容量債變吞吐

第 1 章說批次是把「搬」攤成「算」的籌碼,而籌碼存在 KV cache 裡。傳統做法幫每個 request 按「最長可能」預留一整段連續記憶體——真實利用率只有 20–40%,剩下全是碎片。PagedAttention 把 KV 切成固定大小的 block、像作業系統的分頁一樣按需配置:利用率升到 ~96%, 同樣的 HBM 裝下 2–4 倍的 request,吞吐直接跟著翻。這是 vLLM 起家的那篇論文(SOSP'23)。

2.1 兩筆浪費,一個解法

浪費連續配置的病分頁後
內部碎片預留 max_len,實際長度遠短於它——大半空白block 按需配,只有尾塊平均半空
外部碎片長短不一的釋放留下塞不進新請求的洞所有 block 同尺寸,無洞可留
無法共享相同 system prompt 每人一份block table 指向同一批實體 block

request 拿到的是一張 block table(邏輯位置 → 實體 block id),attention kernel 透過它間接定址—— page table 的翻版。配置、參照計數、驅逐由 KVCacheManager 管理 kv_cache_manager.py:244; block 級機制(free list、ref count、驅逐序)在《vLLM 之書》第 3 章有整章展開。

2.2 複利:前綴快取

分頁的副產品比本體更值錢:block 有了獨立身分,就能內容定址。每個寫滿的 block 以 「鏈到前驅的哈希」入庫 kv_cache_utils.py:577; 下一個帶著相同前綴的 request 直接認領這些 block——不只省了「裝」,連那段 prefill 的「算」都免了。本機實測:

實測 capture E — 同卡同模型;三輪請求,block_size=16,KV 池 810,912 tokens
round 1 (cold)              : prompt_tokens=161, num_cached_tokens=0
round 2 (shared prefix)     : prompt_tokens=159, num_cached_tokens=144   ← 9×16,只有滿 block 入庫
round 3 (identical to rd 1) : prompt_tokens=161, num_cached_tokens=160   ← 161−1,最後一 token 永遠重算

對「同一個長 system prompt 服務所有人」的部署,這是免費的 prefill 摧毀器——第 7 章決策樹裡它是 TTFT 病徵的第一張處方。共享靠 touch 復活 free-but-cached block block_pool.py:597。

選讀:內核考古 + 裝帳本的其他工具

內核在哪?早年的獨立 CUDA kernel paged_attention_v{1,2}.cu 在本書釘選的 HEAD 已被 移除(commit 22a58640b,torch stable ABI 遷移):CUDA 上的分頁定址如今由 FlashAttention / FlashInfer 內核原生承擔 flash_attn.py:67, 只有 ROCm 留著獨立 kernel。「PagedAttention」活在管理層,不再是一個 .cu 檔。

同帳本的其他工具:KV 量化(cache_dtype="fp8" cache.py:76) 一次還兩本帳——容量減半、每步搬的 KV 位元組也減半;CPU offload(vllm/v1/kv_offload/)把閒置 request 的 block 搬去主記憶體;TP 把「裝」的問題攤到多卡(代價是「等」帳本的 all-reduce,見第 8 章地圖第 7 行)。 權重量化(AWQ/GPTQ/FP8)同理:裝與搬雙賺,代價記在「算」(de-quant)上。

第 3 章 · 搬 move × prefill

FlashAttention:不落地的注意力

prefill 是算-bound 的——除了一個著名的例外。標準 attention 會具體化兩個 [N,N] 的中間物(S=QKᵀ 和 P=softmax(S)):N=8192 時各 6,700 萬個元素, 寫進 HBM 再讀回來。搬這兩張表比算它們還貴——攻擊方式是讓它們從頭到尾不存在: 切 tile 在晶片上的 SRAM 裡算完就丟。這就是 FlashAttention,prefill 典型快 2–4×,N 越長賺越多。

層級大小頻寬
SRAM(shared memory / SM)~228 KB~19 TB/stile 的家
HBM(global memory)80 GB~3 TB/s[N,N] 的墳場

唯一的難關:softmax 要全行資訊

分塊 GEMM 免費(部分和可加),softmax 不行——分母 Σexp 和數值穩定的行 max 都是全行函數。 解法是 online softmax:每行只帶三個統計量(running max m、分母 l、 未歸一化輸出 O)跨塊前進;max 更新時把舊累積乘上 α=exp(m−m_new) 追溯重定基準。 真實數字走一遍(重現:softmax_online.py):

s = [2.0, 1.0, 3.0, 0.5] 切兩塊     參考答案 softmax(s)@V = [0.8111, 0.8197]
吃完塊1: m=2.0  l=1.3679  O=[1.0000, 0.3679]
吃完塊2: m=3.0  l=1.5853  O=[1.2858, 1.2995]   # α=exp(2−3)=0.3679 把舊累積重定基準
O/l = [0.8111, 0.8197]  → np.allclose(參考答案) = True   # 不是近似,是同一個數學
負空間:decode 無感
decode 的 Q 是 [1, d]——不存在 N² 中間物,FlashAttention 的招牌收益歸零。 decode 的搬債是另一種:每步掃讀整份 KV cache 與全部權重。那是第 4 章的戰場, 以及 KV 量化 / MLA(把 KV 壓進潛空間,DeepSeek 系 backends/mla/)的地盤。 一句話:先問你的 N² 在哪,再決定買不買這帖藥。
選讀:vLLM 裡的版本與後端選擇

v2(2023)把 Q 移到外層迴圈、一個 thread block 從頭到尾擁有一個 Q tile;v3(2024)是 Hopper 專屬 (TMA、warp specialization、FP8)。vLLM 的 CUDA 後端: flash_attn.py:674(FA2/FA3)、 FlashInfer(decode 特化)、Triton 版,經 selector 按硬體挑 selector.py。 完整演算法推導(rescale 代數、v2 迴圈翻轉、自測題)在《vLLM 之書》第 4 章。

第 4 章 · 搬 move × decode

投機解碼:用一次搬運換 N 個 token

回到 359×:decode 每個 token 都付一次「讀全部權重」的搬運費,而 causal attention 其實能在一次 forward 裡平行評分 N 個位置——只要那 N 個 token 是已知的。投機解碼用便宜的草稿把 「未知的未來」變成「已知的假設」:大模型一次驗 N 個,驗對幾個賺幾個;數學上保證輸出分佈 與不猜完全相同。這是把 decode 偽裝成 prefill 的騙術,而且是合法的。

4.1 三步驟

步做什麼成本
① 猜草稿產 N 個候選(小模型 / EAGLE / n-gram 查表——零參數 ngram_proposer.py:12)遠小於一次目標 FP
② 驗目標模型一次 forward 對 N 個位置產 logits——權重只搬一次≈ 一次普通 decode 步(搬-bound 時)
③ 收從左往右收割;第一個不合處由該位置 logit 出修正 token(免費) rejection_sampler.py:37至少賺 1、至多 N+1 個 token

4.2 本機實測:2.86×

實測 capture S — n-gram 投機(k=5)vs 基線;重複性任務;同卡同模型 batch=1
[S-base ] 256 tokens in 1121 ms -> 228.5 tok/s
[S-ngram] 256 tokens in  392 ms -> 653.7 tok/s      ← 2.86×,零額外參數、零訓練
誠實條款
這個任務(逐字複述段落)是 n-gram 查表的最佳情況——草稿幾乎全中。一般聊天的接受率低得多, 典型收益 1.5–2.5×(EAGLE 系草稿)。最壞情況(全拒)是原速再多付草稿費,約慢 10–25%。 上限:接受率 × (N+1);它只在搬-bound 的 regime 成立——batch 已把算力吃滿時, 驗 N 個真的要 N 倍錢,此藥失效。

4.3 帳本聯動:誰替錯的草稿收屍

verify pass 樂觀寫入全部 N 個位置的 KV;位置 i 被拒後,排程器回滾簿記 num_computed_tokens −= num_rejected scheduler.py:1501, 被拒 slot 回收;快取端上限 min(..., request.num_tokens) 保證未驗證草稿永不進前綴快取—— 第 2 章的共享池不會被猜錯的字污染。完整 KV 紀律(採樣不寫 KV、修正 token 下一輪免費補)見《vLLM 之書》第 6 章。

選讀:草稿家族與同帳本的另一把刀
草稿法怎麼猜錨

第 5 章 · 等 wait

融合與 CUDA Graphs:向啟動費宣戰

decode 的一步是幾百個微小 kernel:80 層 × 每層若干個 RoPE、cache 寫入、norm、投影。 每個 kernel 有固定開工費(啟動 + 讀寫 HBM 一輪),而 batch 小時每個 kernel 只處理一把 token—— 開工費比工作本身還貴。藥方兩帖:把幾張工單合成一張(融合),或干脆把整步的工單序列 錄影重播(CUDA Graphs)。

5.1 案例:RoPE + KV 寫入融合

每個 attention 層開場的兩件小事——旋轉 Q/K、把 K/V 寫進分頁快取——標準形是兩次 launch; 融合 pass 在 FX 圖上 pattern-match 改寫成一次 rope_kvcache_fusion.py:46:

# 融合前 — 每層兩張工單;K 過兩趟 HBM(RoPE 寫出、cache update 讀回)
q, k = rotary_embedding(positions, q, k, cos_sin_cache, is_neox)
unified_kv_cache_update(k, v, layer_name)
# 融合後 — 一張;K 在暫存器裡轉完直接落到分頁 slot,80 層每步省 80 次 launch
fused_rope_and_unified_kv_cache_update(q, k, v, positions, cos_sin_cache, ...)

兩個值得偷走的設計:

  • ≤256 token 才融合 compilation.py:150 —— 又是 regime 分界:大批次(prefill)是算-bound,兩個各自特調的 kernel 反而贏過一個妥協的融合 kernel。 「等」的藥只在「等」是病因時吃。
  • 用 dummy tensor 釘住副作用順序 —— 融合 op 對編譯器是黑箱,cache 寫入不在資料流圖上; op 宣告 mutates_args 並回傳一個下游 attention 消費的假張量,人工造出依賴邊, 防止 Inductor 把寫入重排到讀取之後。每層是否可融合由 backend 回報 backend.py:886(目前主要 ROCm/AITER)。

5.2 核彈:CUDA Graphs

融合是逐張合併工單;CUDA Graph 直接把一整步的 kernel 啟動序列錄下來,之後每步一次 API 呼叫重播—— CPU 端的啟動成本近乎歸零。vLLM 由 cudagraph_mode 控制 compilation.py:590: attention 等自訂 op 是圖上的黑箱,所以有 piecewise 模式——黑箱之間的段落各自成圖。 代價:形狀必須固定(按 batch 大小分桶錄多份)、佔額外記憶體(裝的帳本)、開發時 enforce_eager=True 會把它整個關掉——本書所有 capture 都是 eager 跑的,生產環境的 decode 比書中數字更快。

選讀:融合 pass 家族與 VllmBackend

同一套 pattern-match 機制上還掛著 RMSNorm+Quant、AllReduce+RMSNorm、Attention+Quant、 Activation+Quant、SP 改寫(把 TP 的 all_reduce 換成 reduce_scatter+all_gather,省中段冗餘 sequence_parallelism.py:136)等, 開關集中在 PassConfig compilation.py:139。 底座是 VllmBackend——vLLM 插進 torch.compile 的自家後端(切圖、掛 pass、管 CUDA graph) backends.py:800。 編譯管線全景與「lowering 路徑」分類學:Lowering-Path Explorer 與《vLLM 之書》第 8–9 章。

第 6 章 · 算 comp + 裝 fit

LoRA:當形狀不配合硬體

「算」的債很少是總 FLOPs 太多——通常是形狀餵不飽硬體。LoRA 是完美案例: 每個 adapter 只是兩片瘦矩陣(秩 r=8–64),數學上便宜到不像話,但 Tensor Core 的積木每維至少 ~16, r=8 的收縮維讓它一半算力空轉;更糟的是多租戶批次裡每一列要用不同的 adapter,cuBLAS 根本沒有這種介面。 答案與 FlashAttention 同款:為這個形狀手寫 kernel。

6.1 裝的那一半:一個底座,千個房客

100 個客戶 × 70B 全微調 = 100 份 140 GB,經濟上不存在。LoRA 凍結底座、每客戶只帶 ΔW ≈ B·A(10–100 MB):「裝」的帳本從 O(客戶數 × 模型) 降到 O(模型 + 客戶數 × adapter)。 前提是 serving 時不合併(y = Wx + (α/r)B(Ax))——合併回 W 就退化成一人一份。 adapter 的載入/預熱/驅逐由 manager 管 model_manager.py:71。

6.2 算的那一半:BGMV / SGMV

標準 GEMV:  y = W·x                      整批共用一個 W
BGMV:       y[i] = W[adapter_id[i]]·x[i]  批中每列各自索引自己的 adapter

所有 adapter 打包進一大塊 HBM 張量、adapter_id→offset 查表、一次 launch 內各列讀各的分片 ——5 個客戶的混合批次 ≈ 一次普通 GEMV 的成本。SGMV 再解形狀問題:r 維歸約放進 shared memory 用一般 CUDA core 做(放棄餵不飽的 Tensor Core),按 adapter 分段打包攤掉啟動費 punica_base.py:22。 雙 stream 執行把 LoRA 路徑疊到底座 GEMM 旁邊而非串在後面(VLLM_LORA_ENABLE_DUAL_STREAM envs.py:284)——用「等」帳本的技巧付「算」的債。

同一個模式,到處都是
「通用 kernel 在特化形狀上失效 → 手寫」是「算」帳本的萬用鑰匙:Marlin/Machete 之於 W4A16 反量化 GEMM、 fused MoE 之於「每 token 選 2 個專家」的稀疏批次、 fused_moe/layer.py:100、 Punica 之於 skinny LoRA。附錄目錄裡標 的大多屬於這族。 LoRA 完整機制(B 零初始化、哈希隔離、七個掛點)在《vLLM 之書》第 7 章。
第 7 章 · 決策

服務慢——動哪裡?

優化選錯帳本是白花錢:給算-bound 的 prefill 上投機解碼、給搬-bound 的 decode 換更強的 GEMM kernel,都是安慰劑。診斷永遠先於處方——挑一個病徵,看它被三個問題路由到哪本帳、哪帖藥。

自己量,別猜——三個一線指標
  • TTFT vs ITL:OpenAI 相容端點回 stream 時第一個 chunk 的延遲 vs 後續間隔; 或離線用本書 capture_regime.py 的方法直接量。
  • GPU 利用率 + 記憶體水位:nvidia-smi dmon;利用率低而延遲高 → 等; 記憶體貼頂、log 出現 preemption → 裝(vLLM 會印 KV 池大小與 preemption 警告)。
  • vLLM 自帶指標:prefix cache 命中率、佇列深度、preemption 次數——都在引擎的 metrics 輸出裡; 排程機制見《vLLM 之書》第 2 章。

病徵常是複合的:OOM 逼你縮 batch,縮了 batch 吞吐掉進「搬」的坑——此時先還「裝」的債 (量化/分頁),batch 回來了,「搬」自然攤薄。這正是四本帳的連動,也是第 8 章地圖的讀法。
