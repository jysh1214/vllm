FEYNMAN LEAD · 先用白話說 vLLM 是一台「讓大語言模型同時服務很多人」的引擎。你送進一句話,它安排這句話跟其他幾百句話 共乘同一顆 GPU:誰先上車、誰的記憶放哪裡、車子怎麼開得快,分別由排程器、KV cache 管理器、 和一堆手寫的 GPU 內核決定。這本書就是跟著一個 request 上車到下車的完整路線,把每一站拆開看。

1.3 心跳:EngineCore 的一步

整個系統的「一拍」,就是這個函式的一圈。這是 HEAD 上的真實程式碼(節錄),三個載重呼叫標了色:

真實原始碼(節錄)vllm/v1/engine/core.py:479
def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
    """Schedule, execute, and make output."""
    if not self.scheduler.has_requests():
        return {}, False
    scheduler_output = self.scheduler.schedule(...)          # ① 計畫
    future = self.model_executor.execute_model(scheduler_output, non_block=True)  # ② 執行
    grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
    ...
    model_output = future.result()
    ...
    engine_core_outputs = self.scheduler.update_from_output(  # ③ 對帳
        scheduler_output, model_output)
    return engine_core_outputs, ...

① 計畫:排程器選出這一步的批次並分配 KV block(不跑模型);② 執行:executor 讓所有 worker 跑一步 forward; ③ 對帳:把真實採樣結果寫回簿記、偵測停止條件、釋放完成的 request。 request 可以在任何一拍上車或下車——這就是 continuous batching,第 2 章會看到它其實是「湧現」出來的,不是特別寫的功能。

選讀:同一個迴圈的管線化版本 step_with_batch_queue

當 executor 支援併發(如 pipeline parallel),EngineCore 改用 vllm/v1/engine/core.py:519 的 step_with_batch_queue():同樣三個呼叫,但多個 batch 同時在飛,schedule 與 update 交錯進行, 讓 PP 的各 stage 不空轉。語意不變,只是重疊。

面試官會這樣問 · 第 1 章

Q1 「vLLM 有沒有 fork PyTorch?它跟 PyTorch 的邊界劃在哪?」

展開參考答案
沒有。四個縫合點全是 PyTorch 官方擴充機制:模型是 nn.Module 子類;自製內核用 torch.library 註冊成 torch.ops._C.*;編譯是把 VllmBackend 插進 torch.compile(backends.py:800); 其餘(排程/KV/服務)只是使用 PyTorch API。判斷準則:PyTorch 提供機制(mechanism),vLLM 提供服務策略(policy)。

Q2 「如果把 EngineCore 的 update_from_output 拿掉,系統會壞在哪裡?」(反事實)

展開參考答案
schedule() 只做樂觀計畫:它假設這一步排下去的 token 都會算完,先把簿記推進(第 2 章的 _update_after_schedule)。沒有 ③ 對帳,真實採樣結果永遠不會寫回:停止條件測不到(request 永不結束)、 投機解碼被拒絕的 token 不會回滾(KV 簿記永久錯位)、完成的 request 不會釋放 block(記憶體漏光)。 計畫與現實的縫合就在 scheduler.py:1501。

第 2 章 — 排程器:沒有 prefill,也沒有 decode

FEYNMAN LEAD 直覺上,LLM 推理有兩種工作:「讀完你的問題」(prefill,一次算很多字)和「一個字一個字回答」(decode,一次算一個字)。 vLLM 排程器最漂亮的一招是:它根本不區分這兩件事。每個 request 只有兩個數字——「已經算到哪」和「想算到哪」—— 排程器每一拍發一筆共用的 token 預算,讓大家的進度往目標追。讀題、續讀、答題,全是同一條算式。

位置:vllm/v1/core/sched/scheduler.py; 由第 1 章的 EngineCore 每步驅動,吐出 SchedulerOutput,吃回 ModelRunnerOutput。

2.1 統一調度模型:兩個計數器

原始碼裡最重要的一段註解(HEAD 實碼):

真實原始碼(節錄)vllm/v1/core/sched/scheduler.py:399
# NOTE(woosuk) on the scheduling algorithm:
# There's no "decoding phase" nor "prefill phase" in the scheduler.
# Each request just has the num_computed_tokens and num_tokens_with_spec.
# num_tokens_with_spec = len(prompt) + len(output) + len(spec_token_ids).
# At each step, the scheduler tries to assign tokens to the requests
# so that each request's num_computed_tokens can catch up its num_tokens_with_spec.
計數器意義錨點

num_tokens_with_specprompt + 已產出 + 投機草稿 的總長(「想算到哪」)request.py:251

每步想做的工作量就是差值:num_new_tokens = 目標 − 已算,排程器發給它 min(num_new_tokens, 剩餘預算, …)。四種看似不同的情況,同一條算式(點列高亮):

情況已算 vs 目標本步獲配
新 prompt(俗稱 prefill)0 vs 1000up to 1000(或一個 chunk)
prompt 算到一半(chunked prefill)600 vs 1000up to 400
生成中(俗稱 decode)1000 vs 10011
decode+5 個投機草稿1000 vs 1006up to 6

所以「prefill vs decode」只是「num_new_tokens 大或小」,排程器從不寫 if 去分支。 chunked prefill 和 continuous batching 因此是湧現的性質,不是特別實作的功能——半熟的 prompt 和正在生成的 request 由同一段程式碼排程。

2.3 schedule():兩階段分預算

schedule()(scheduler.py:396) 對一筆共享預算 token_budget = max_num_scheduled_tokens 跑兩個階段。用步進器走一遍:

STEP 1 / 6 · Phase 1 — 先服務 running

從 self.running 前端(最老)往後走,對每個 request 算 num_new_tokens = 目標 − 已算,夾到剩餘預算、長 prefill 門檻、max_model_len−1 之內。 正在 decode 的 request 這裡通常拿到 1。

STEP 2 / 6 · 要記憶體

對這個 request 呼叫 kv_cache_manager.allocate_slots(...) (scheduler.py:535)。 這是記憶體壓力咬人的地方——回 None 就是「沒位子了」。

STEP 3 / 6 · 配不到 → 搶佔別人

配置失敗就搶佔:FCFS 挑 running 最後一個(最年輕)、PRIORITY 挑優先度最低者,呼叫 _preempt_request(scheduler.py:1142): 釋放它全部 KV、num_computed_tokens 歸零、標 PREEMPTED、塞回 waiting 前端。然後重試配置; 如果被搶的就是自己,本步放棄。

搶佔是總體損失(整個 prompt 要重算),靠前綴快取(第 3 章)通常能救回大半。

STEP 4 / 6 · Phase 2 — 拉 waiting 進場

只有在沒發生搶佔且預算有剩、running 數未達上限時才做。從 waiting 前端 peek: 被遠端 KV 或 LoRA 上限擋住的先跳過;新 request 先查前綴快取 (scheduler.py:725 → get_computed_blocks)——命中的部分視同已算,prefill 直接免費。

STEP 5 / 6 · chunk 或整段

num_new_tokens = 全長 − 已算。超出預算時:chunked prefill 關閉 → 直接停止收新客; 開啟 → 夾到預算、先排一個 chunk。配置失敗這裡只 break——waiting 讓位給 running,此階段絕不搶佔 (scheduler.py:905, admission gate 參數 full_sequence_must_fit 見 :914)。成功則移入 running。

STEP 6 / 6 · 打包 + 樂觀推進

計畫打包成 SchedulerOutput(scheduler.py:1094)。 然後是關鍵一手:_update_after_schedule (scheduler.py:1166) 在模型還沒跑時就先 num_computed_tokens += 本步排的量——這讓下一步能立刻續排同一 request 的下一個 chunk, 不用等結果。猜錯的部分(投機被拒)由對帳修正。

2.4 update_from_output():對帳

模型跑完,真實結果回來(scheduler.py:1501),對每個被排的 request:

  1. 修投機簿記:排了 N 個草稿、實際產出 len(generated) 個 → num_accepted = len(generated) − 1,被拒的 num_rejected = N − num_accepted 從樂觀計數回滾:num_computed_tokens −= num_rejected。這是投機解碼 KV 修復的排程器端(第 6 章)。
  2. append 採樣 token 並跑停止偵測:EOS、stop string、max_tokens / max_model_len、結構化輸出文法。
  3. 停了就釋放:_free_request(scheduler.py:2097) 把 KV block 還給池子,id 進 finished_req_ids。
  4. 組 EngineCoreOutput 按 client 分組回傳串流。

2.5 continuous batching 是湧現的

排程器裡沒有任何一行程式碼實作「continuous batching」。它是三件事的合力: Phase 1 每步重排所有 running(decode 各推進 1)+ Phase 2 預算一有剩就放新人進同一批 + 對帳立刻退役完成者、釋放預算與 KV。於是 request 在任意步邊界上下車;油門是 token 預算(不是 request 數), 這就是為什麼同一步裡能混著一個大 prefill chunk 和幾百個 1-token decode。

不變量(記這五條就夠)
  • 一筆預算、兩個階段。先 running 後 waiting;唯一的例外是搶佔把預算「還」給 running。
  • 已算數在計畫時推進,不在執行時。只有投機被拒才回滾。
  • 搶佔是全損。歸零重算,前綴快取通常能救。
  • schedule() 計畫,update_from_output() 對帳。模型嚴格跑在兩者之間。
  • 排程器不碰 GPU 記憶體。只透過 KVCacheManager 拿/還 block;配置失敗是驅動搶佔的唯一訊號。

第 3 章 — KV Cache:GPU 裡的虛擬記憶體

FEYNMAN LEAD 模型每讀過一個字,都會留下一份「筆記」(K/V 張量),之後每個新字都要回頭翻所有舊筆記。 問題是:筆記本要多大?傳統做法幫每個人預留「最長可能」的整本——大部分頁數永遠空白。 vLLM 把筆記本拆成固定大小的活頁(block),誰需要就發誰一頁,用完回收; 兩個人前面寫的內容一樣,就共用同幾頁。這正是作業系統分頁記憶體的翻版——搬進了 GPU。

位置:vllm/v1/core/。 排程器(第 2 章)只跟 KVCacheManager 說話;它的「配不出來」= 排程器的搶佔訊號。

3.1 為什麼要分頁:PagedAttention 的問題意識

連續配置(per-request 一大塊、按最大長度預留)造成:內部碎片(實際長度遠短於上限)、 外部碎片(長短不一的空洞塞不進新請求)、無法共享(相同 system prompt 每人一份)。 實務上有效利用率只有 20–40%;分頁後接近用滿。這是 vLLM 起家的論文級想法(PagedAttention, SOSP'23): block table = page table,「頁」= HBM 裡固定大小的 KV 塊。

選讀:那 paged attention「內核」在哪?(HEAD 上的考古注記)

早年 vLLM 有獨立的 CUDA 內核 csrc/attention/paged_attention_v{1,2}.cu 直接讀 block table。 在本書釘選的 HEAD 上,這兩個檔案已被移除(commit 22a58640b「Migrate attention and cache kernels to torch stable ABI」):CUDA 平台的分頁讀取已由 FlashAttention / FlashInfer 內核原生支援 (backends/flash_attn.py), 只有 ROCm 還留著獨立的 paged attention 內核 (csrc/rocm/attention.cu)。 「分頁」的本體如今活在管理層(本章)+ 各 attention backend 的 block-table 定址裡。

同樣要釐清:PagedAttention 不是 swap-to-disk——預設 block 只活在 HBM。 把 KV 搬出 GPU 的是疊在上面的另一層:CPU offload(vllm/v1/kv_offload/) 與 KV-transfer connectors(NIXL / LMCache / MoonCake…,見第 10 章目錄)。

  • 最後一個 token 永遠重算:max_cache_hit_length = num_tokens − 1——就算 100% 命中, 也要留一個 token 進 forward,才有 logit 可以採樣。

第 4 章 — FlashAttention:不落地的注意力

FEYNMAN LEAD 注意力運算會產生一張「每個字對每個字」的巨大打分表。傳統做法把整張表寫進顯示卡的大倉庫(HBM)再讀回來加工—— 路程比計算本身還貴。FlashAttention 的想法:把表切成小塊,每一小塊都在晶片上的小快取(SRAM)裡算完就丟, 整張大表從頭到尾不存在。唯一的難關是 softmax 需要「整行」的資訊——它用一套帶著跑的統計量解決了這件事。

在旅程中的位置:第 2、3 章決定「算哪些 token、K/V 放哪」;本章是 forward pass 裡真正執行注意力的內核。 vLLM 的 CUDA 後端:backends/flash_attn.py(FA2/FA3)、 flashinfer.py、 triton_attn.py、 mla/(DeepSeek 系)。

4.1 問題:HBM 頻寬,不是算力

標準注意力具體化兩個大中間物:S = QKᵀ 與 P = softmax(S),形狀都是 [N, N]。 N = 8192 時各約 6,700 萬個元素,都要寫進 HBM 再讀回。而 GPU 的記憶體階層(H100 量級):

層級大小頻寬
暫存器~256 KB / SM~30 TB/s
SRAM(shared memory / L1)~228 KB / SM~19 TB/s
L2~50 MB~5 TB/s
HBM(global memory)80 GB~3 TB/s

SRAM 比 HBM 快約 6 倍、小約 35 萬倍。「IO-aware」的意思就是:演算法設計的目標是少過幾次 HBM,而不是少做幾次乘法。 (術語註:FlashAttention 文獻裡的 SRAM 指 per-SM 的 shared memory——程式設計師用 __shared__ 顯式控制的那層,不是 L2。)

4.2 唯一的難關:softmax 要全行資訊

分塊 GEMM 天生可行(部分和直接相加),但 softmax 需要整行的 max 和分母總和——單看一個 tile 是算不出來的。 解法是 online softmax:每個 query row 只帶三個統計量往前跑:

m : 純量        目前為止的 running max
l : 純量        running 分母  Σ exp(sᵢ − m)
O : 向量[d]     running 分子  Σ exp(sᵢ − m) · vᵢ

[N, N] 的中間物被壓成每行 O(d) 的狀態——靠的是 softmax 的 max-平移不變性與 exp(a)·exp(b)=exp(a+b)。 當 running max 從 m 跳到 m_new,把累積中的 O 和 l 同乘 α = exp(m − m_new),舊貢獻就被追溯重定基準。

4.3 走一遍真實數字

1 個 query row、4 個 KV 位置切成 2 塊、d=2。分數 s = [2.0, 1.0, 3.0, 0.5], V = [[1,0],[0,1],[1,1],[−1,2]]。下列數字是實際計算輸出(重現腳本見版本記錄):

STEP 1 / 4 · 參考答案(標準 softmax)

整行一次算:softmax(s) @ V = [0.8111, 0.8197]。這是等會兒 online 版要逼近——不,是精確重現——的目標。

STEP 2 / 4 · 吃第一塊 s=[2.0, 1.0]

初始 m=−∞, l=0, O=0。塊內 max 是 2.0 → m=2.0; P = exp([2,1]−2) = [1, 0.368] → l = 1.3679,O = [1.0, 0.3679]。 注意:這是未歸一化的累積,不是真的 softmax——分母還沒收齊。

STEP 3 / 4 · 吃第二塊 s=[3.0, 0.5] — rescale 登場

塊內出現 3.0 > 2.0 → m_new=3.0,舊基準錯了。修正係數 α = exp(2−3) = 0.3679,把舊的 l、O 各乘 α 再累加新塊: l = 0.3679×1.3679 + exp([3,0.5]−3).sum() = 1.5853,O = [1.2858, 1.2995]。 這一乘就是 FlashAttention 的全部魔法——過去的每一項 exp(sᵢ−2) 被追溯改成 exp(sᵢ−3)。

STEP 4 / 4 · 最後除一次

O / l = [0.8111, 0.8197] —— 與 STEP 1 的參考答案逐位一致(np.allclose → True)。 FlashAttention 不是近似:同樣的數學,只是不同的計算順序(浮點捨入差異之內)。整個過程中 [N,N] 打分表的任何完整版本都不曾存在於 HBM。

選讀:完整迴圈虛擬碼 + v2 的迴圈翻轉
m = -inf; l = 0; O = 0
for each (K_block, V_block):
    S_blk = Q_blk @ K_blockᵀ          # tiled GEMM #1,SRAM 內
    m_new = max(m, max(S_blk))
    α     = exp(m − m_new)            # 舊貢獻的重定基準係數
    P_blk = exp(S_blk − m_new)        # 局部「未歸一化」指數
    l     = α·l + sum(P_blk)
    O     = α·O + P_blk @ V_block     # tiled GEMM #2,SRAM 內
    m     = m_new
return O / l                          # 全程唯一一次除法

常見誤解:「每塊做一次 partial softmax」。不存在這種東西——softmax 需要全域分母,塊內只能累積未歸一化的 exp;歸一化只發生在最後那一次除法。S_blk、P_blk 是暫存器/SRAM 裡的 scratch,塊用完即棄。

v1→v2→v3:v2 把 Q 移到外層迴圈(一個 thread block 從頭到尾擁有一個 Q tile,免去跨塊同步 O)+ 減少非矩陣乘運算,約 2× v1; v3 是 Hopper 專屬(TMA 非同步搬運、warp specialization、FP8)。

Q1 「為什麼分塊對 matmul 是免費的,對 softmax 卻要發明 online 演算法?」(機制)

展開參考答案
matmul 沿收縮維的部分和滿足結合律,塊算完直接加即可。softmax 的分母 Σexp 和數值穩定所需的行 max 都是全行函數,塊內無從得知。online softmax 利用兩個代數性質補救:max-平移不變(結果不因基準平移而變) 與 exp(a−m₁)·exp(m₁−m₂)=exp(a−m₂)(舊貢獻可事後重定基準)。缺一不可—— 步進器 STEP 3 的 α=0.3679 就是後者的具體數字。

Q2 「把 α rescale 拿掉,輸出會錯多少?什麼情況下恰好不錯?」(反事實)

展開參考答案
舊塊的每一項還在用舊基準 exp(sᵢ−m_old),相對新塊被放大 exp(m_new−m_old) 倍—— 在數值範例中不 rescale 會得到 O/l = [0.876, 0.777] 而非 [0.811, 0.820](權重偏向舊塊)。 恰好不錯的唯一情況:running max 從未更新(第一塊就含全行最大值)——這也是為什麼 bug 可能在測試小例上潛伏。

Q3 「一個 8K 上下文的聊天服務,90% 時間在 decode。FlashAttention 對它的幫助有多大?該優化什麼?」(trade-off)

展開參考答案
幫助集中在 10% 的 prefill(首 token 延遲);decode 的 Q 是 [1,d],無二次方中間物,FlashAttention 基本無感。 decode 的錢要花在:KV cache 讀取量(量化 FP8/INT8、MLA 壓縮)、批次併發(第 2 章 continuous batching 把頻寬攤給更多請求)、 或直接減少步數(第 6 章投機解碼)。這正是「先認清 bound 在哪,再選優化」的教科書案例。

第 5 章 — 分散式:一個模型,很多顆 GPU

5.5 SP:TP 的搭檔,不是新的軸

純 TP 有個浪費:兩次 all-reduce 之間的區域(RMSNorm、殘差加)在每個 rank 上重複執行—— 每個 rank 都對全長序列做一模一樣的 norm、存全長的啟動值。SP(sequence parallelism)把這些區域沿 token 維切開。 它不是獨立軸(沒有 _SP coordinator)——它是 torch.compile 的圖改寫 pass,複用 TP group (sequence_parallelism.py:136, 由 CompilationConfig.enable_sp 開啟):

純 TP :  all_reduce(x)                    → rms_norm(...)
SP    :  reduce_scatter(x, dim=0) → rms_norm(...) → all_gather(dim=0)

關鍵性質:reduce_scatter + all_gather 搬的總位元組數 = 一次 all_reduce (後者內部本來就是前兩者)——通訊量不變,但兩者之間每個 rank 只處理 1/tp 的 token。

RMSNorm(Y[2×4]) 在兩卡各做一次 ← 一模一樣的工作 × 2(冗餘)

5.6 EP:換一種集合通訊的軸

MoE 層用路由器替每個 token 挑 top-k 個專家(如 256 選 2)——參數巨大、每 token 實際算的很少。 256 個專家單卡裝不下,TP 式「每卡都存全部、各存一片」又浪費;EP 直接把整顆專家按 id 分家: determine_expert_map(expert_map_manager.py:22) 把 global_num_experts 均分到 ep_size 個 rank,建 global_id → local_id 映射(不在本卡為 −1)。 每卡持有完整的少數專家——與 TP「每卡持有全部專家的切片」相反。

EP 1 / 5 · 本地路由

各 rank 對自己批次裡的 token 跑 router(linear→softmax→top-k):Rank 0 的 t0 選中 {E0, E3}, 但 E3 住在 Rank 1。

EP 2 / 5 · DISPATCH(all-to-all ①)

把每個 token 洗牌到「擁有它選中專家」的 rank (dispatch,base_device_communicator.py:336)。 洗完:每個 rank 手上只剩「要給我的專家算的 token」。

EP 3 / 5 · 本地專家計算

各 rank 用自己的專家跑被送來的 token。E0(t0) 在 Rank 0、E3(t0) 在 Rank 1,同時進行。

EP 4 / 5 · COMBINE(all-to-all ②)

結果按原路送回 token 的出生 rank (combine,:373)。

EP 5 / 5 · 本地加權和

回到 Rank 0:t0_out = w0·E0(t0) + w3·E3(t0)。一層 MoE 完成——代價是兩次 all-to-all。

為什麼是 all-to-all 而不是 all-reduce?因為切的東西不同: TP 切一個 matmul,各 rank 產出同一批 token 的部分和 → 要加總(all-reduce); EP 切「哪些 token 去哪」,各 rank 產出不同 token 的完整結果 → 要搬運(all-to-all)。沒有任何東西需要跨 rank 相加。

第 6 章 — 投機解碼:把 decode 偽裝成 prefill

FEYNMAN LEAD 生成是一個字一個字來的,而每產一個字,GPU 都得把幾十 GB 的模型權重從頭到尾讀一遍——讀的時間遠多於算的時間。 但有個怪事:讓模型「一次檢查 5 個字」跟「產 1 個字」花的時間幾乎一樣(反正都要讀一遍權重)。 投機解碼便宜地猜 5 個字,讓大模型一口氣驗完:猜對幾個賺幾個,猜錯也不虧——輸出經數學證明與不猜完全同分佈。

位置:vllm/v1/spec_decode/(各種 proposer)、 v1/sample/rejection_sampler.py(驗收)。 與第 2 章(排程器簿記)、第 3 章(KV 快取紀律)深度咬合——這章會把那兩條伏筆收回來。

6.1 為什麼有這個空子可鑽

目標forward 次數權重 HBM 掃讀每次產出 logits
prefill 1000-token prompt111000
decode 1000 個新 token100010001

同樣產出 1000 份 logits,prefill 讀一次權重,decode 讀一千次——prefill 的每 token 成本低約三個數量級, 因為權重讀取攤在所有位置上。這不是數學更便宜,是 HBM 攤提。慢的原因只有一個:decode 的每個位置依賴前一個 還沒被採樣出來的 token,依賴鏈強迫序列化。

但注意 causal attention 的性質:只要 N 個 token 已知,一次 forward 就能平行算出 N 個位置的 logits (訓練時的 teacher forcing 就是這樣)。投機解碼的本質:用草稿模型把「未知的未來」變成「已知的假設」, 讓 decode 得以用 prefill 的形狀跑——verify pass 就是一次 seq_q=N 的迷你 prefill。

6.2 演算法:猜 → 驗 → 收

STEP 1 / 4 · 草稿猜 N 個

小模型自迴歸地產 N 個候選(典型 N=3–8):[d1..d5]。它也是一個字一個字猜,但每步成本遠低於大模型。 草稿來源可以是獨立小模型、EAGLE(spec_decode/eagle.py)、 Medusa、n-gram 查表(零參數!ngram_proposer.py)等。

STEP 2 / 4 · 目標模型一次驗完

把 [d1..d5] 餵給大模型跑一次 forward:Q:(heads, 5, d)、 K/V:(kv_heads, k+5, d)。causal mask 保證位置 i 的 logit 只看得到 [context, d1..dᵢ]—— 與逐字 decode 算出來的 logits 數學上完全相同,只是一次拿到 N+1 份(含驗最後一格的 bonus)。

STEP 3 / 4 · 從左往右收割

逐位置比對:greedy 下「argmax(Lᵢ) == dᵢ₊₁ 就收」;遇到第一個不合就從那個位置的 logit 採樣一個修正 token 並停止。 注意修正 token 是免費的——verify pass 本來就算出了那份 logit。所以每輪至少賺 1 個 token(等同 vanilla decode), 至多 N+1 個。

STEP 4 / 4 · 帳目(筆記中的示意計算,非實測)

70B 目標 100ms/FP、1B 草稿 5ms/FP、N=5:草稿 25ms + 驗證 100ms;若收 4 個 token → 31ms/token, 對照 vanilla 的 100ms/token ≈ 3.2×。最壞情況(全拒):同樣一次目標 FP,只多付 25ms 草稿費, 仍產出 1 個 token——虧損有下限,獲利無上限到 N+1。

6.3 KV 紀律:錯的草稿誰來擦

核心不變量(貫穿 prefill、decode、投機): 採樣產生 token 但不產生它的 K/V;K/V 由下一個「把它當輸入吃進去」的 forward pass 產生。 verify pass 樂觀地寫入了全部 N 個草稿位置的 K/V,位置 i 被拒後:

位置寫了什麼處置誰處置
0 .. i−1被接受的草稿保留—
i .. N−1被拒的草稿丟棄排程器:num_computed_tokens −= num_rejected 回滾樂觀簿記(scheduler.py:1501,第 2 章伏筆)
修正 token x沒有 K/V(採樣不寫快取)下一輪 verify 把 x 當第一個輸入,順手補上免費

快取端的防線在第 3 章出現過:cache_blocks 的上限取 min(..., request.num_tokens)—— 未驗證的草稿 token 永不進前綴快取,拒絕不會污染跨請求共享。排程端在 SchedulerOutput 裡也看得到這套管線的接口 (capture C3 的 scheduled_spec_decode_tokens、num_invalid_spec_tokens 欄位)。

選讀:隨機採樣下的正確性(rejection sampling)與各種草稿來源

T>0 時逐位置做:以機率 min(1, p(d)/q(d)) 接受草稿 d(q=草稿分佈、p=目標分佈); 拒絕時從 max(0, p−q) 重新歸一化後採樣。經典 rejection sampling 證明(Leviathan et al. 2023): 輸出分佈恰等於只跑目標模型——與 q 無關。爛草稿傷速度,永不傷品質。 實作:v1/sample/rejection_sampler.py。

草稿法怎麼猜

EAGLE 系掛在目標 hidden state 上的一層小 transformer(eagle.py)

Q1 「不用草稿模型,隨便餵 5 個 token 進 verify pass,反正 logits 都會算出來——為什麼不行?」(機制)

展開參考答案
每份 logit 是條件分佈 P(next | context, d1..dᵢ)——它只在「條件前綴可信」時有用。 餵垃圾,L_pre 之後的每份 logits 都以虛構的過去為條件,無法用來產出正確序列的下一個字;能收割的只剩 1 個 token, 跟 vanilla decode 一樣。草稿模型的全部工作就是讓條件前綴可信到 logits 變得可用。

Q2 「批次很大、GPU 已經算滿的時候,投機解碼還賺嗎?」(trade-off)

展開參考答案
不賺,甚至虧。整個把戲建立在「memory-bound 時驗 N 個 ≈ 驗 1 個」;compute-bound(大批次把算力吃滿)時 verify N 個位置真的花 ~N 倍時間,草稿還照付。所以它是 decode 專屬、且偏好中小批次/延遲敏感的優化—— 與第 4 章的 FlashAttention(prefill 專屬)恰好互補,兩者合起來覆蓋兩種 regime。

Q3 「位置 2 被拒。寫出接下來一輪開始前,KV cache 和兩個排程計數器分別發生什麼。」(trace)

展開參考答案
KV:位置 0–1(接受)保留;位置 2–4(被拒)的 slot 由排程器回收——num_computed_tokens −= 3 (update_from_output 的回滾); 修正 token x 從 L₂ 採樣、沒有 K/V。前綴快取不含任何草稿(第 3 章 min(..., num_tokens) 上限)。 下一輪:num_tokens_with_spec 重算(含新草稿),x 作為 verify 輸入的第一格,其 K/V 順帶補齊。

第 7 章 — LoRA:一個底座,千個房客

FEYNMAN LEAD 一百個客戶各要一個「微調過的 70B 模型」,難道存一百份 140GB 的權重?LoRA 的觀察:微調對權重的改動 本質上是低秩的——可以用兩片薄薄的矩陣(常常只佔原本的 0.1%)表達。於是底座只存一份、凍結不動, 每個客戶帶自己的兩片小矩陣來「租房」。vLLM 要解的是下一步:讓同一批次裡不同客戶的請求 在一次 forward 裡各用各的補丁。

7.1 分解:W 不動,學 BA

原式:    y = W·x                          W ∈ R^(d_out × d_in)(凍結)
LoRA:    y = W·x + (α/r)·B·(A·x)          A ∈ R^(r × d_in), B ∈ R^(d_out × r)
          r ≪ min(d_in, d_out),常見 8–64;A 隨機初始化、B 初始化為零 → 訓練起點 BA=0,行為=底座

d=4096、r=16 的一層:全微調 1,677 萬參數 vs LoRA 13.1 萬——128×。整個 70B 的 adapter 常在 10–100MB。 LoRA 只掛在線性投影上:QKVO 與 MLP 的 gate/up/down 七處;norm、softmax、RoPE、activation 都沒有可學矩陣,掛不了。

7.2 為什麼 serving 必須「不合併」

模式算式優劣
合併W' = W + (α/r)BA,跑 W'x零額外開銷一個複本只能服務一個 adapter——多租戶死
不合併每次 forward 都算 Wx + (α/r)B(Ax)一批次可混多個 adapter每投影多兩個小 matmul

vLLM 的世界(第 2 章:同一批次裡混著所有人的請求)只能選不合併。剩下的問題是:那兩個小 matmul 怎麼算才不慢?

7.3 Punica 內核:BGMV / SGMV

批裡 5 個請求來自 5 個客戶,樸素做法要嘛拆成 5 次 forward(吞吐 ÷5)、要嘛每人一份合併權重(記憶體 ×100)。 正解是讓內核「每列查自己的補丁」:

標準 GEMV:  y = W·x                     整批共用一個 W
BGMV:       y[i] = W[adapter_id[i]]·x[i]  批中每列各自索引自己的權重

所有 adapter 的 A、B 打包進一大塊 HBM 張量,adapter_id → offset 查表,一次 kernel launch 內各列讀各的分片—— 5 個不同 adapter 的批次 ≈ 一次普通 GEMV 的成本。 另一半問題是形狀:LoRA 的收縮維只有 r=8~64,Tensor Core(希望每維 ≥16)效率極差。 SGMV 把 r 維的歸約放進 shared memory 用普通 CUDA core 做、按 adapter 分段打包多個請求進同一次呼叫—— 與 Marlin 之於 W4A16 同屬「小而怪的形狀,手寫專用內核」家族。 實作:lora/punica_wrapper/punica_base.py:22。

面試官會這樣問 · 第 7 章

Q1 「B 為什麼初始化為零?A 也一起零可以嗎?」(機制)

展開參考答案
B=0 使 BA=0:訓練第 0 步的模型行為與底座完全一致,微調從「不破壞」出發。 A、B 同時為零則梯度也為零(∂loss/∂A 經過 B、反之亦然),永遠學不動——所以 A 隨機、B 零,缺一不可。

Q2 「r=8 的兩個 matmul 為什麼讓 cuBLAS 難受?SGMV 的兩個手段各解什麼?」(機制)

展開參考答案
Tensor Core 的 MMA tile 每維至少 ~16,收縮維 r=8 時一半算力空轉,而且每個 adapter 的矩陣小到攤不平 launch 開銷。 SGMV:(1) r 維歸約改在 shared memory 用 CUDA core 做——放棄 Tensor Core 而不是餵不飽它; (2) 按 adapter_id 分段,把多個 adapter 的工作打包進一次 launch——攤掉啟動成本。 本質與第 3 章分頁同一個哲學:通用機制(cuBLAS/連續配置)在特化形狀上失效時,為那個形狀寫專用機制。

Q3 「兩個客戶用同一個 base、不同 adapter,發同一段 system prompt——前綴快取能共享嗎?」(綜合)

展開參考答案
不能,而且不能是對的:LoRA 掛在 QKV 投影上,同一段文字經不同 adapter 產生的 K/V 不同。 機制上由第 3 章的 extra_keys 保證——block hash 折入 LoRA id (kv_cache_utils.py:539),兩人的哈希天然不同。 若 adapter 只掛 MLP 不掛 attention,理論上 K/V 相同、可共享,但 vLLM 不做這種細粒度判斷——安全優先。

第 8 章 — 編譯與融合:torch.compile 上的 vLLM

FEYNMAN LEAD GPU 做事有固定的「開工費」:每叫醒一個 kernel、每往大倉庫(HBM)走一趟,都要付。 decode 每步的運算又碎又小,開工費常常比工作本身還貴。融合(fusion)就是把好幾件小事合成一張工單: 少叫醒幾次、少跑幾趟。vLLM 不自己寫編譯器,而是在 torch.compile 的管線裡插入自己的改寫規則—— 第 5 章的 SP 是一條,這章的主角 RoPE+KV 寫入融合是另一條。

8.1 底座:VllmBackend

模型類掛上 @support_torch_compile (decorators.py:115)後, forward 被 torch.compile(backend=VllmBackend) 包住 (wrapper.py:166,backend 由 init_backend,:90 決定)。 VllmBackend(backends.py:800)做三件事: 切圖(attention 等自訂 op 是 Dynamo 眼中的黑箱,圖在黑箱處斷開,段落分別交 Inductor)、 掛 pass(post-grad 圖改寫:各種融合、SP)、管 CUDA graph(整圖或分段捕捉)。 這正是第 1 章縫合點 3 的全貌——vLLM 租用 PyTorch 的編譯管線,只添自己的規則。

8.2 案例:RoPE + KV 寫入融合

每個 attention 層開場的兩件簿記小事:① RoPE 旋轉 Q/K;② 把 K/V 寫進分頁快取的指定 slot。標準形是兩次 kernel launch:

# 融合前 — 兩張工單
q, k = rotary_embedding(positions, q, k, cos_sin_cache, is_neox)
unified_kv_cache_update(k, v, layer_name)
# 融合後 — FX 圖上 pattern-match 改寫成一張

融合內核把 Q/K/V 讀進來一次:RoPE 在暫存器/SRAM 內轉完,轉好的 K 與原樣的 V 直接落到分頁快取 slot—— K 原本要過兩趟 HBM(RoPE 寫出、cache update 讀回),現在一趟。80 層的模型每個 decode step 省 80 次 launch。 Pass 本體:passes/fusion/rope_kvcache_fusion.py:46。

  • 為什麼是 compile pass 而不是手寫呼叫:(1) 能否融合取決於每層的 attention backend——pass 逐層問 fused_rope_kvcache_supported()(v1/attention/backend.py:886), 目前主要 ROCm/AITER 系支援,不支援就跳過;(2) 副作用排序——融合 op 宣告 mutates_args=["query","key"] 並回傳一個 dummy tensor 讓下游 attention 消費, 這條假資料流是防止 Inductor 把「cache 寫入」重排到「attention 讀取」之後的圍欄。

展開參考答案

第 9 章 — CPU 下沉鏈:aten::mm 與 RVV 之路

9.3 決策:RVV 內核放哪層?

先看兩個事實,再看四個選項。事實一:vLLM 已內建 RVV 向量抽象—— csrc/cpu/cpu_types_riscv*.hpp,由 #elif defined(__riscv_v) 選中 (cpu_types.hpp:16); 且泛型微 GEMM MicroGemm<ISA::VEC> (micro_gemm/cpu_micro_gemm_vec.hpp:103) 以向量抽象為模板參數——RVV 建置下它已經會撿到 RVV 型別。事實二(實測):

supported_vec_isa_list: [VecAMX, VecAVX512VNNI, VecAVX512, VecAVX2, VecNEON, VecSVE256]
any RVV / riscv: False        （torch._inductor.cpu_vec_isa 實際列舉)
PathRVV 落在哪工程量覆蓋控制權
A — OpenBLAS-RVV(鏈①)OpenBLAS(多目標已有 RVV 微內核,常是「選對 TARGET 建對庫」)+ 重建 PyTorch 連結低只有 fp32 GEMM無
B — VecRVV + at::vec(鏈②)PyTorch 上游:Inductor codegen 加 VecRVV ISA + aten/src/ATen/cpu/vec 加 RVV 後端很高(持續)所有編譯的原生 op(但 GEMM 仍外呼)低
C — oneDNN-RVV(鏈③)上游 oneDNN(或經 FETCHCONTENT_SOURCE_DIR_ONEDNN 掛本地 fork,cpu_extension.cmake:312)很高bf16/int8 GEMM無(x86-JIT 中心的庫)

建議(帶理由的決策記錄):

  • 最快拿到能跑的 RVV GEMM:Path D。RVV vec 型別、微 GEMM 鷹架、custom op 註冊機制全部在庫內; 工作是保證 RVV vec 型別實作微 GEMM 用到的操作 + 在 dispatch_cpu_unquantized_gemm 加一個分支。 黑箱性質(9.2)在此變成優點:任何 compile mode 下都生效。代價:GEMM 的打包/分塊/調優從此歸你養。
  • 整模型覆蓋的正解:Path B。唯一能讓 fusion/elementwise/norm 全部向量化的路——但 capture C5 顯示 RVV 在上游還不存在, 這是 PyTorch core 的長期工程,且 Inductor 預設把 GEMM 外呼(extern kernel)——就算 B 完成,快的矩陣乘還是要靠 A 或 D。
  • A 是零程式碼的 fp32 過渡方案(LLM 推理主力的 bf16/int8 幫不上);C 近期不實際(oneDNN 的 RISC-V 支援還在實驗階段)。
面試官會這樣問 · 第 9 章

Q1 「為什麼設了 backend=inductor,模型的 GEMM 還是跑在 oneDNN?」(機制,本章核心)

展開參考答案
因為終端在 load 時就綁死了:CPU 預設綁 onednn_mm——一個沒有 fake impl 的自訂 op, Dynamo trace 到它只能原樣保留(黑箱),Inductor 無從 codegen。想讓 Inductor 生成 GEMM, 得先讓綁定 fall through 到 F.linear(鏈①的原生綁定),compile mode 才有分岔的餘地。 錨:dispatch_cpu_unquantized_gemm,utils.py:228。

Q2 「Path B 全部做完,為什麼矩陣乘還是不快?」(trade-off)

展開參考答案
Inductor 的 CPU 管線對 aten.mm 預設走 extern call(交回 ATen→BLAS),自產 C++ GEMM 只在 max-autotune 的模板路徑出現、且競爭力有限。B 的價值在 GEMM 周邊:融合的 elementwise/norm/activation 全面向量化。 矩陣乘本體的 RVV 還是要 A(BLAS)或 D(自寫)。這也是為什麼結論是「B 管面、A/D 管點」。

Q3 「Path D 寫好的 RVV GEMM,在 torch.compile 下需要重新驗證嗎?」(綜合)

展開參考答案
功能上不用擔心被編譯器改寫——它是無 fake impl 的自訂 op,任何 compile mode 都原樣呼叫(9.2 的不變性, 這正是 AMX SGL 內核的既有行為)。但要付黑箱稅:Inductor 無法把它與鄰近 op 融合,圖也會在它處切開; 若需要 compile 期 shape 特化,得補 meta/fake impl——那就要重新考慮排序圍欄(第 8 章 dummy tensor 的教訓)。
