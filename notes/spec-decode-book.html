前言

一個觀念

LLM 一次只能吐一個 token,而且每吐一個都要把整顆大模型跑一遍——慢的不是「算」,是「搬權重」。 推測解碼讓一個便宜的「草稿者」先猜未來好幾個 token,再讓大模型用「一次」forward 把這些猜測全部驗證掉; 猜對的就一次收下好幾個,猜錯的丟掉。最關鍵的是:最後輸出的文字分佈,和大模型自己一個一個生出來的一模一樣——數學上無損。

整本書都掛在這一句話上:

猜得便宜 ① Propose → 一次驗證 ② Verify → 只留下 target 同意的前綴 ③ Accept,而且可證明無損。

整個系統就是這三拍的迴圈。全書用同一套顏色詞彙,在每張圖、每個元件都代表同一件事:

Propose · 草稿者(drafter)便宜地猜 K 個 token
Verify · 目標模型(target)一次 forward 跑完所有草稿位置
Accept · target 同意、收下的 token
Reject · 第一個不同意處,丟棄並用 target 取代
Bonus · 全部接受時,額外多送一個 token
關於這本書
這本書解釋的是你這個 vLLM fork(/home/alex/vllm)的實作。每個論述後面的 檔案:行號 就是回到原始碼查證的捷徑——polished 的解釋不能取代驗證。 行號可能隨 commit 漂移;對不上時,搜尋指名的符號即可。
第 1 章

為什麼要「猜」,而不是直接算?

「直接算」n 個字,意思就是讓大模型一個接一個算 n 次——而這正是我們想避開的那件慢事。 推測解碼的全部把戲,就是用一個便宜的東西「猜」,把 n 次大模型的序列計算,換成 1 次大模型的平行驗證。

為什麼不能一次算出 n 個字

關鍵在於 LLM 的定義方式:它算的是「給定前面所有字,下一個字是什麼」,也就是 P(下一個字 | 前面的字)。問題來了——

算 t+1   需要 → [1..t]               ✅ 有
算 t+2   需要 → [1..t, t+1]          ❌ t+1 還沒生出來
算 t+3   需要 → [1..t, t+1, t+2]     ❌ 連環缺

這是一條因果鎖鏈:第 k 個字是算第 k+1 個字的輸入。所以你無法「一次直接算出」n 個字—— 必須 算一個 → 餵回去 → 再算下一個,天生是序列的。「直接算 n 個」= 跑 n 次大模型,這就是普通解碼,也就是慢的本體。

這條鎖鏈有個名字:自迴歸(autoregressive)

自(auto)= 自己;迴歸(regressive)= 根據過去的值預測下一個。合起來就是: 模型把自己剛產生的輸出,當成下一步的輸入,一個接一個地往下生。(這個詞本來是統計學講時間序列的,LLM 借用了它。)

"今天天氣"        → 輸出 → "很"
"今天天氣很"      → 輸出 → "好"    # 把上一步的「很」接回去了
"今天天氣很好"    → 輸出 → "。"    # 又把「好」接回去

每一步的輸入 = 原句 + 模型自己到目前為止生出來的所有字。target 大模型是自迴歸的, 這就是生成天生序列、無法一次算完 n 個的原因。大多數草稿方法(EAGLE / MTP / draft_model)也是自迴歸的; Medusa 不是——它的頭彼此不互餵,一次出 n 個。

那為什麼「猜」反而快?

兩個事實湊在一起:

  1. 大模型一次 forward,其實能同時算出「每個位置」的下一字機率——前提是那些位置的字你已經有了。 訓練、以及處理 prompt(prefill)時就是這樣平行算的。卡住生成的不是「算」,而是「未來的字還沒有,沒法當輸入」。
  2. 解碼是記憶體頻寬瓶頸,不是算力瓶頸。batch 很小時,一次 forward 的時間幾乎全花在「把幾十 GB 權重從 HBM 搬一遍」, 真正算一個 token 只用到 GPU 一丁點算力。所以算 1 個 token 和算 n 個 token,牆鐘時間幾乎一樣(都只搬一次權重)。

於是訣竅出來了:讓便宜的草稿者先猜出 g₁ g₂ … gₙ,把猜測填進輸入;現在每個位置都「有字了」, 大模型就能用一次 forward 平行算出這 n 個位置的正確機率,再核對哪些猜中。切換下面看這兩條路徑的差別:

同樣產出 4 個 token,大模型被呼叫的次數差很多。

等等——草稿不也是「一個一個」猜?

對,大多數草稿方法確實也是自迴歸的,只是跑在便宜的小模型上。哪些「一次出 n 個」、哪些「一個接一個」,要看方法:

方法怎麼產 n 個草稿一次嗎?
EAGLE / EAGLE3 / MTP / draft_model用便宜的 draft 模型一個接一個猜:跑一次 → 草稿₀ → 餵回去 → 再跑 → 草稿₁ → …不是,自迴歸 n 次
Medusan 個預測頭在同一次 forward 各猜一個未來位置是,一次
n-gram從前文找到重複片段,把後面接的 k 個字抄過來(查表)是,一次

完整六種方法的對照(含「是不是自迴歸」欄)在第 4 章;EAGLE 的逐步鏈畫在第 5 章。

重點釐清:序列本身不是問題
你可能會問:「咦,你不是說『序列地算』就是慢的根源嗎?EAGLE 不也是序列?」——關鍵在這: 序列本身不是問題;序列地跑「昂貴的大模型」才是問題。 推測解碼把那條序列鎖鏈搬到了便宜的 draft 模型上;昂貴的 target 在整個過程只跑一次(平行驗證全部 n 個位置)。 
# 都產出 ~n 個 token
普通解碼:   n 次 × 昂貴 target forward
推測解碼:   n 次 × 便宜 draft forward  +  1 次 × 昂貴 target forward
            └─ 序列,但很便宜 ─┘             └─ 平行,只一次 ─┘

draft 模型很小(EAGLE 常常只有 1 層,還重用 target 的 hidden state),所以那幾次便宜的 forward, 遠小於省下的 (n−1) 次昂貴 target forward——這就是淨賺的地方。也因為 draft 仍要做這些序列工作, 所以「draft 太大」或「n 太大」會吃掉收益(第 6 章的取捨)。

「讓大模型自己一口氣吐 n 個」不行嗎?

可以,而且真的有人這樣做——這正是 Medusa(多接幾個預測頭)和 MTP(checkpoint 內附的多 token 預測層,見第 4 章)。 但它們在「還不知道第 t+1 個字」的情況下去預測第 t+2 個字,數學上必然是近似的(等於對未知的 t+1 取了某種平均)。 所以它們吐出來的 n 個字,本質上仍是「猜」,而不是精確值。

這就是為什麼:無論草稿從哪來(獨立小模型、額外的頭、還是查表),它都只是 drafter,都還得經過驗證—— 這樣才能保住「輸出分佈和大模型自己慢慢算的一模一樣」的無損保證。

一句話
不是「不直接算」,而是「直接算」=「序列跑 n 次大模型」就是慢的根源。 猜測 + 平行驗證,是用便宜的近似換掉昂貴的序列依賴,再用驗證把精確性補回來。

所以加速的上限,就是「平均每次 target forward 能吐出幾個 token」——這個數字叫 acceptance length(接受長度),是第 6 章的主角。它也解釋了為什麼推測解碼 不會憑空變快:草稿者若猜得太爛,接受率低,反而白付了草稿成本。

第 2 章

一個 step,從頭到尾

在 vLLM 裡,一個 engine step 走五拍:把上一步的草稿重新注入 → target 一次 forward → rejection sampler 接受前綴 → drafter 立刻提議下一批 → 寫回 request。這五拍就是執行期的骨架。

主路徑在 vllm/v1/worker/gpu_model_runner.py,排程在 vllm/v1/core/sched/scheduler.py。每一步都標了它在原始碼的位置:

第 3 章 · 互動

接受判定:為什麼無損

這是推測解碼最反直覺、也最重要的一點:用一個爛草稿者不會讓輸出變差,只會讓它變慢。 下面這個模擬器讓你親手試:點每個草稿 token 切換「target 同不同意」,看最終吐出什麼。
點 token 切換 target 是否同意。第一個不同意處之後,全部丟棄。
↓ target 只跑了 1 次 forward,卻產出了 ↓

它在背後做的事(數學)

設草稿者對某 token 的機率是 q(x),target 是 p(x)。隨機採樣模式下:

  1. 接受該草稿的機率 = min(1, p(x)/q(x))。程式碼直接是這條比值測試:
    rejection_sampler.py:817  accepted = draft_prob > 0 and target_prob / draft_prob >= uniform_prob
  2. 被拒時,從「殘差分佈」p_res(x) ∝ max(p(x) − q(x), 0) 重新採一個取代 token:
    rejection_sampler.py:914  prob = max(target_prob − draft_prob, 0)
  3. 全部接受時,額外補一個直接從 target 採的 bonus token:
    rejection_sampler.py:827 / :760  if not rejected: 寫入 bonus
為什麼這樣就「無損」?(展開看一行證明)

某 token x 被輸出的總機率,是「接受它」加上「先拒絕別的、再從殘差抽到它」:

P(輸出 x) = q(x)·min(1, p/q) + P(拒絕)·p_res(x)
         = min(p(x), q(x))     + max(p(x) − q(x), 0)
         = p(x)                               # ← 恰好是 target 分佈,與 q 無關

所以每個輸出 token 的邊際分佈恰好等於 target 的 p,跟草稿品質 q 完全無關。 這就是 Leviathan 等人的推測採樣演算法,程式碼在類別 docstring 直接引用:

rejection_sampler.py:40  https://arxiv.org/abs/2211.17192
Greedy(temperature=0)走另一條確定性捷徑

不擲骰子、不採殘差:接受 ⟺ 草稿 token 等於 target 的 argmax;否則直接放 argmax。 所以 greedy 路徑連殘差採樣都不會呼叫。

rejection_sampler.py:748-752  token_id = target_argmax_id; rejected = draft_token_id != target_argmax_id
對抗式驗證:confirmed,但有兩個前提
我派了一個 agent 專門去「反駁」這個無損主張,結論是成立,但必須講清楚兩點:
  • 「無損」是相對於「套用 temperature / top-k / top-p 之後」的 target 分佈,不是 raw logits—— 這些約束在 softmax 前就套好了(rejection_sampler.py:510 apply_sampling_constraints)。
  • 有一個非預設的 synthetic 模式(config/speculative.py:191)會用固定接受率、無視真實機率—— 那條路徑不是無損的,但它是 opt-in 的 benchmarking 開關,正式預設是 standard。

小細節:-1 是哨兵值——接受的 token 從 index 0 連續排好,第一個 -1 就是第一個拒絕點, 所以「數有幾個非 -1」就是接受長度(gpu_model_runner.py:1513)。ngram 這種沒有 draft 機率的方法,把 q 視為 1,接受準則退化成 p(x) ≥ u。

第 5 章 · 互動

EAGLE 深入

EAGLE 是目前最常用的方法。訣竅:draft head 不從零開始,它重用 target 的內部 hidden state (target 對上一個 token 的「想法」)加上下一個 token 的 embedding,從這裡便宜地一個接一個猜出多個 token。
切換看 EAGLE3 多了哪一步。
EAGLE3 多的這一步: 先把 target 多層(預設 layer 2, n/2, n−3)的 hidden state 串接後用 combine_hidden_states() 融合降維,才開始猜;而且它有自己較小的 draft 詞表,再用 d2t 映射表 scatter 回 target 全詞表。
llm_base_proposer.py:456 method in ("eagle3","dflash") llama_eagle3.py:378 combine_hidden_states
這個迴圈最容易誤解的一點
combine_hidden_states(融合 target 多層特徵)只在第一步做。在自迴歸迴圈裡,draft head 吃的是 它自己上一步輸出的 hidden state(llm_base_proposer.py:604)——所以 target 的特徵只直接影響第一個草稿 token, 後面是 draft head 純粹的遞迴。
兩個值得知道的工程細節
  • 這個 fork 的 EAGLE 產生的是線性 chain(一條 [batch, K]),不是 tree;tree 介面存在但這條路徑沒用上。
  • 草稿 token 在餵回前會 cast 成 int32(llm_base_proposer.py:581),因為 argmax 出來是 int64 會弄壞編譯後的 draft model。
  • EAGLE1 的融合是 fc(cat(input_embeds, hidden_states)),fc 輸入維度 = 2×hidden_size(llama_eagle.py:107)。
第 6 章 · 互動

它有沒有賺?

效果由 acceptance length(接受長度) 衡量,它基本上就是加速倍率:平均每次昂貴的 target forward 吐出幾個 token。 普通解碼恆為 1。

公式很直接(vllm/v1/spec_decode/metrics.py:95):

mean_acceptance_length = 1 + (num_accepted_tokens / num_drafts)
                          ↑ 這個 +1 是「全接受時的 bonus token」;scheduler 先把它從接受數扣掉(scheduler.py:1398)

但接受率會隨位置衰減

前 3 根是實測值;第 4 根起是示意外推(假設每位置再乘 ~0.68 衰減),用來看曲線變平、邊際遞減的形狀,並非實測。

核心取捨
num_speculative_tokens 猜越多,無論接不接受都要付草稿與驗證成本;但後面位置接受率低 → 邊際遞減。 草稿太差或猜太長,推測解碼可能反而變慢。上面這條曲線(也匯出成 Prometheus counter vllm:spec_decode_num_*) 就是你判斷「草稿者有沒有賺回成本」的依據。

別混淆兩個比率:draft acceptance rate = 接受數/草稿token數(每 token 命中率,metrics.py:88); mean acceptance length = 1 + 接受數/草稿批數(每次驗證吐幾個 token,metrics.py:95)。只有後者直接對應加速。

參考

詞彙表

自迴歸 autoregressive
把模型自己剛生出來的輸出,當成下一步的輸入,一個接一個往下生。target 大模型是自迴歸的(所以生成是序列的、無法一次算完 n 個);EAGLE / MTP / draft_model 的草稿也是,Medusa 不是。
drafter / 草稿者
便宜地猜未來 token 的東西。可以是查表(ngram)、額外的頭(Medusa)、小 transformer(EAGLE)、或一整顆獨立小模型(draft_model)。
target / 目標模型
真正要服務的大模型。它的輸出分佈是「無損」要保住的對象。
propose / verify / accept
一個 step 的三拍:猜 K 個草稿 → target 一次 forward → 接受同意的前綴。
rejection sampling
用 min(1, p/q) 接受、被拒則從殘差 max(p−q,0) 重採的演算法,保證輸出分佈 = target 分佈。
bonus token
當一批草稿全被接受時,額外從 target 採的一個 token。每個 step 至少輸出 1 個 token,就是靠它。
acceptance length
